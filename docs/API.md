# API Google backend

Браузер обращается к Next.js через `services/api.ts`. Серверный транспорт `services/google-client.ts` отправляет Apps Script JSON `{payload, signature}`. Payload — сериализованный объект `action`, `data`, `token`, `requestId`, `timestamp`; signature — HMAC-SHA256 строки payload с GOOGLE_API_SECRET. Допуск времени — 5 минут. Секрет никогда не передаётся клиенту.

Ответ: `{success:true,data:...}` либо `{success:false,error:{code,message,status}}`. Apps Script передаёт статус ошибки внутри JSON; Next возвращает соответствующий HTTP-статус. Основные статусы: 400 неверные поля, 401 вход необходим, 403 нет доступа, 409 конфликт, 429 лимит входа, 503 недоступность сервиса.

| Действие | Назначение и доступ |
| --- | --- |
| bootstrap | Первоначальное создание су-шефа, только при разрешённой первоначальной настройке |
| login / logout | Вход по логину и паролю / завершение сессии |
| getCurrentUser / getKitchen | Пользователь, станции, задачи и текущие результаты после входа |
| getAdditional | Дополнительные задания с фильтрацией по правам |
| getUsers / getRoles | Управление аккаунтами су-шефом; доступные роли |
| getStatistics | Историческая статистика по правам роли |
| getPhoto | Приватное фото с проверкой доступа |
| shift | Начало/завершение смены повара на станции |
| createUser | Су-шеф создаёт повара, су-шефа, шеф-повара или аудит |
| updateUser | Су-шеф редактирует аккаунт и роль; последний су-шеф защищён; смена роли отзывает сессии |
| task | Управление станционными задачами су-шефом |
| assignAdditional | Назначение дополнительных задач су-шефом |
| complete | Выполнение задачи поваром, 1–4 обязательных фото и проверка назначения |
| getActivity | Текущая календарная неделя, сводка и уровни пользователей; су-шеф, шеф-повар, аудит |
| additionalType | Создать/изменить тип: optional id, title, isActive; только су-шеф |
| snapshot | Служебная фиксация предыдущего дня после 04:00 МСК |

Точные поля и типы: `types/models.ts`, валидация команд: `google/src/core.ts`, HTTP-маршруты: `app/api`. Права повторно проверяет Apps Script, независимо от интерфейса.

Сессия хранится в HttpOnly cookie, в Sheets — только хеш токена с датой истечения. Новый пароль хешируется scrypt на сервере; при входе проверяется Apps Script. Изменяющие запросы используют UUID Idempotency-Key: завершённый повтор возвращает сохранённый результат; другой payload с тем же ключом отклоняется. Записи защищены ScriptLock и атомарным Sheets batchUpdate.

Фотография декодируется и сжимается сервером в WebP, затем повторно проверяется backend (до 3 МБ, до 1600 px, без анимации). Base64 используется только при передаче, в таблице хранятся ссылки на приватные файлы (одна строка для одного фото, JSON-массив для нескольких).

Cloud Scheduler вызывает POST `/api/cron` с `Authorization: Bearer <CRON_SECRET>`. Этот отдельный секрет также остаётся на сервере. Настройка: `SETUP_GUIDE.md`.

HTTP: GET `/api/activity`, POST `/api/additional-types`. При назначении сохраняется title_snapshot; при выполнении completed_by_user_id берётся из сессии, клиентское поле автора игнорируется.

Удаление: POST `/api/users` с `{action:"delete",id}` → Apps Script `deleteUser`. Только manage, защита последнего су-шефа, идемпотентное мягкое удаление и отзыв сессий.

## Несколько фотографий

POST `/api/complete`: multipart-поля `category`, `id` и от 1 до 4 повторяющихся файлов `photos[]`. Старое поле `photo` для одного файла также поддерживается; смешивать форматы нельзя. Каждый сжатый файл — WebP/JPEG до 3 МБ; запрос — до 13 МБ. Все файлы проходят проверку и сохраняются в рамках одного выполнения задачи. При ошибке одного файла выполнение не создаётся.

Внутреннее действие `complete` принимает `photosBase64: string[]`, `mimeType: "image/webp"` (старое `photoBase64` поддерживается для одного снимка). Подписанный входящий запрос Apps Script ограничен 18 МБ с учётом base64. `Task.photoCount` возвращает количество фото, `photoId` остаётся идентификатором выполнения.

GET `/api/photos/{category}/{photoId}` возвращает первый снимок. Для остальных используется `?index=1`, `?index=2`, `?index=3`. Внутреннее действие `getPhoto` принимает целочисленный `index` (по умолчанию 0); доступ сначала проверяется к выполнению целиком. Несуществующий индекс отклоняется. Все фотографии защищены одинаковыми правами и `private, no-store`.
